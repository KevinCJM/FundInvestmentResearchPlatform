# 代码提交、Bot 审核与合并全流程

本文详细说明本项目从接到任务到合并、发布、回滚的执行顺序，供人类和 AI 共用。规则以 [提交、审核与合并规范](branch-submission-rules.md) 为准；本文负责解释操作逻辑，不另立豁免条件。入口为 [AGENTS.md](../../AGENTS.md)，GitHub 配置事实见 [分支保护实现](branch-protection.md)。

## 1. 整体流向与责任

正常流向为：**确认任务与授权 → 确认分支和工作区 → 开发及验证 → 自审核 → commit/push → 开发分支向 Dev 提 PR → Bot 审核及意见处理 → 合并核查 → merge commit → 验证远端结果**。需要发布时，再走一次 Dev → main 的 PR 流程。

提交到开发分支、推送开发分支、创建 PR、审核通过、合并到 Dev、发布到 main 是不同动作。AI 必须按人类已经授权的范围执行；同一事项已有明确授权时无需重复询问，但“修复代码”不会自动扩大成“推送、发布或绕过审核”。

普通协作者需要一位有写入或管理权限、且不是 PR 作者的审核者提供有效 Approve。Owner KevinCJM 可以豁免普通批准要求；其他 Admin 不自动获得这个例外。无论由谁执行正常合并，都必须先取得 Bot 针对最新提交的有效通过结果。

Owner 可以例外合并没有通过 Bot 审核的 PR。AI 代 Owner 行使这项例外时，必须先得到人类明确允许并回复 Bot；GitHub 登录身份不会替 AI 完成这一步判断。

## 2. 接到任务：先明确范围

先分清本次任务涉及哪些模块、哪些动作获准执行，以及哪些功能明确排除。阅读 AGENTS.md、相关 AI Hermes 路由、提交规范和本文；有 CodeGraph 索引时，先通过知识图谱定位相关实现，再以当前源码、配置和测试核实行为。

此时检查当前目录、分支、远端、工作区和暂存区。已有改动默认属于原任务或并行任务，不能因它们恰好位于同一个目录就纳入本次提交。对于一个文件中混合的多个功能，应按内容拆分提交，必要时在隔离 worktree 验证准备提交的版本。

禁止为了得到“干净工作区”擅自 reset、clean、stash 或覆盖别人的文件。发现无法安全区分的重叠时，先保留现场、说明具体冲突，再取得必要信息。

## 3. 确定分支和开发基线

先 fetch 真实的 `Dev`、`main`，确认祖先关系及最新提交，不把本地同名分支当作远端事实。通常从最新 Dev 创建 `codex/<主题>`；人类明确要求在当前开发分支工作时，按该授权执行，不擅自迁移或重命名分支。

开发变更必须通过开发分支 → Dev PR。main 只接受同一仓库的 Dev → main PR。回滚和 main 历史回同步 Dev 也必须通过 PR，不允许直接向 main/Dev 推送、强推或删除分支。

## 4. 开发、测试与文档同步

只修改本次获准的功能和必要依赖。先追踪输入、实际调用链和输出，再实施改动；不能为了缩小测试范围而保留同一功能的新旧双实现，也不能借重构删减未授权能力。

按改动选择测试。接口变更检查前后端契约；计算变更遵守 NJIT、预热、确定性和数值边界要求；界面交互变更补充浏览器验证。纯文档变更只需验证文档一致性、链接、路由和相应配置。不能用静态检查代替实际运行，也不能把上次通过的结果当作本次新证据。

同步本次需求及设计文档。重要入口、测试、配置或隐藏契约发生变化时，按 AI Hermes 所有权更新路由信息并运行 evolve/validate。结果要区分“当前已验证”“仅有历史证据”和“尚未验证”。

## 5. 提交前自审核

自审核的对象是**准备提交的精确内容**。同时查看已跟踪差异和新增文件，确认没有混入未完成模块、正式数据、凭据、缓存、构建产物或本地临时文件。

对于共享文件中的混合改动，先形成独立可运行的提交候选，再测试该候选。不能在混合工作区测试成功后，就推断剔除另一项功能后的提交同样可用。

发现问题应先修复并复验。自审核只是提交质量检查，不代替后续 Bot 审核，也不是给自己的 GitHub PR 伪造一个 Approve。

## 6. Commit、Push 与创建 PR

确认已经获得相应动作的授权后，只暂存本任务内容，再检查 staged diff。提交说明描述最终行为，推送当前开发分支；不直接推送 main/Dev。

创建以 Dev 为目标的 PR，正文说明问题、实现范围、验证结果、已知限制，并提供需求文档及技术文档的实际链接。共享上位设计可以引用，但须明确本 PR 实现的边界，不能把未完成规划写成已经交付。

草稿 PR 不得直接合并。新增提交后，旧审核不能覆盖新代码；需要重新核对 PR 的完整 HEAD SHA、测试及审核证据。

## 7. 等待并识别 Bot 审核

读取真实 Bot 作者的 PR 总评、review 和行内意见，确认对应的是当前最新提交。当前指定 Bot 为 `chatgpt-codex-connector[bot]`；模仿它发言的普通账号不算审核。

“审核任务完成”和“审核通过”不同。例如 Summary 显示 `Completed`，但同一轮还有 P1/P2 建议，只能认定审核已经完成且发现问题。绿色 `branch-policy` 表示分支来源符合要求，并不证明 Bot 认可代码。

有效通过证据必须能够对应到当前 HEAD，并明确表示通过或没有问题。对于 Bot 用点赞表达无问题的情况，还要核实对应本轮的完成记录及无问题结论；一个无法关联提交的历史点赞不能放行。既不能靠“暂时没有评论”推断通过，也不能靠 AI 自己关闭讨论改变审核事实。

Bot 尚未开始、仍在运行、失败、超时、结论不明确或只审核了旧提交时，保持“尚未通过”，等待或重新请求审核。不得自动超时放行，也不得把未收到审核结果解释成 Bot 的建议不合理。

## 8. 逐条处理 Bot 意见

每条意见都要回到当前源码、需求契约、调用链和可复现证据，判断它是否成立。Bot 不是天然正确，也不能因为意见不符合开发者预期就忽略。

成立的问题先修复，补充能暴露问题的回归检查，执行相应验证并推送；在对应线程说明修改及证据，再请求 Bot 复审最新提交。仅回复“已修复”或点 Resolve，不会自动产生 Bot 的通过结果。

对于确属误报或不适用的建议，整理对应代码、测试结果和反证。可以通过正常澄清促使 Bot 重新审核；如果仍未获得通过且希望例外合并，进入下一节，不直接使用 Owner 权限跳过。

所有未处理的实质问题都要说明。不能通过删除审核、撤销 `CHANGES_REQUESTED`、修改保护规则或隐藏评论让 PR 看起来像已通过。

## 9. AI 代 Owner 绕过 Bot 的唯一例外流程

首先，AI 完成本地核实，把待处理事项整理成一个具体、可审阅的请求：PR 编号、目标分支、完整 HEAD SHA、Bot 意见链接、为什么认为建议不合理、支持结论的代码或测试、剩余风险，以及准备回复 Bot 的原文。

然后，AI 主动向人类请求本次绕过许可并等待答复。人类的“帮我合并”“继续提交”、此前其他 PR 的授权、没有回复或经过较长时间，都不能代替这项许可。获得对同一提交、同一组意见的明确允许后，不再为同一事项重复询问。

允许的表达例如：“同意 PR #N 在提交 `<完整SHA>` 上绕过这两条 Bot 意见；按已核对的理由回复后合并。”这只是授权文本示例，AI 不得替人类发送、生成一条冒充人工批准的评论，或从沉默中推定同意。

获得允许后，先在每个相关 Bot 线程中实际回复，说明原建议、当前实现为何不同、对应的代码/测试证据和此次人类允许。若人类明确接受一个真实问题带来的风险，必须如实记录“接受风险及其影响”，不能为了满足形式要求把合理意见说成误报。回复失败时先恢复留痕，不能跳过回复直接合并。

例如，误报回复可以说明：“该建议假定 A 路径仍在使用；当前调用链实际进入 B，位置和测试如下。Owner 已针对提交 `<SHA>` 明确允许本次例外合并。”必须用真实路径和实际测试替换示例内容；“我认为没问题”“所有测试都绿了”本身不足以反驳具体问题。

最后再次读取 HEAD 和 Bot 意见。只要出现新提交，原授权即不覆盖它；出现新增或实质变化的争议，也需重新说明并取得相应授权。授权完成、逐条回复已经发布、其他合并条件满足后，才能使用 Owner 的 PR 内豁免执行合并。

这是一项 AI 执行纪律。本项目不通过另建 AI 账号、不同令牌或专门授权服务区分人类与 AI。AI 不能以“GitHub 允许这个账号合并”为理由省略人类请求。

## 10. 合并前最后核对

刷新 PR 信息，确认它仍然 Open、非 Draft、来源和目标正确、没有冲突、必要检查已经完成并通过。普通协作者还要核实有效 Approve；Owner 可以豁免普通批准，但不能把这种权限等同于 Bot 审核已经通过。

单独核对 Bot：要么有当前 HEAD 的有效通过证据，要么已经走完本次 Owner 例外。Bot 已通过时，AI 按已有的普通合并授权执行；仅因 Owner 无人工 Approve，不需要额外申请一次 Bot 例外。

目标分支如果前进，应检查最新合并结果和影响范围，必要时解决冲突、验证集成；实质差异发生变化时重新核对审核和授权。不能将来源正确、权限正确、无冲突、检查通过混成一个“都绿了”的判断。

执行时使用 merge commit，并通过 `--match-head-commit` 匹配刚核查的完整 SHA。`--admin` 是调用既有 Owner 权限的参数，不是授权凭证，也不允许临时放宽其他保护。

## 11. 合并之后

读取 PR 状态、目标分支、合并时间及 merge commit，fetch 目标分支并核实该提交确实进入目标历史。需要严格核对时，比较实际合并树与测试过的合并结果。

向人类简要报告 PR 链接、提交和合并结果、验证证据及仍留在本地的其他任务。使用过 Bot 例外时要明确标记，不能把它记成“Bot 已通过”。合并后出现迟到的实质审核意见，继续按当前代码核实并通过修复 PR 处理，不改写已经合并的历史。

保护原工作区中的其他改动。可以清理本任务创建的临时 worktree 和进程，但不能借收尾清理并行任务或正式数据。

## 12. 发布与回滚

Dev 合并完成不代表已经发布 main 或部署。发布必须另有相应授权，并创建同一仓库 Dev → main PR，审核完整累积差异、最新 Bot 结论、必要测试及 main 的 `branch-policy`。

开发 PR 的 Bot 通过或 Owner 例外，不能自动复用为发布 PR 的许可。部署也按授权及环境要求单独验证，不能把 merge 成功写成生产部署成功。

回滚使用 Git revert 等版本能力，在开发分支提交可审核的撤销变更，再按同一 PR、Bot 审核和合并流程进入目标分支。不能直接改写 main/Dev 历史，也不能在业务源码中保留备用旧实现充当回滚开关。

## 13. 文档要求与 GitHub 技术状态

本流程中的“Bot 未通过不得正常合并”是所有执行者必须遵守的规范。当前仓库 `.github/workflows/branch-policy.yml` 只检查 main 的来源，现有三组 ruleset 分别约束 PR-only、普通批准和 main 分支方向；它们没有实现独立的 Bot 内容检查。

因此，文档与 AI 路由更新不能表述为 GitHub 已自动拦截所有 Bot 未通过的 PR，也不能表述为已经修改远端设置。AI 必须主动读取 Bot 证据并遵守流程，Owner 例外中的人类允许由 AI 自觉请求；若后续另行建设或部署 Bot required check，须同步实现文档并读取远端实际状态验收。


文档同步按[文档维护协议](documentation.md)执行，提交前检查暂存候选。仓库新增的 Documentation 工作流负责结构检查和影响报告；是否已在远端运行或配置为 required check 须单独核实，不能替代 Bot 审核或改变本规范的授权条件。
